# Durable data volumes

Terrarium's Pocket PC and Alpine x86_64 profiles can attach real writable block volumes whose data is stored in the browser's IndexedDB. These are independently owned data filesystems: stopping, resetting, or deleting the machine does not erase the saved volume. The RISC-V profiles do not currently implement this attachment API.

## Guest behavior

Each new volume is an empty ext2 filesystem generated by `src/lib/volume-format.ts`. The formatter creates superblocks, block groups, allocation bitmaps, inode tables and the root directory directly from code. It does not download or redistribute an operating-system disk image. Inputs are the disk size and filesystem UUID; the same inputs produce identical bytes. The sparse formatter preserves the earlier single-group layout byte for byte for disks up to 128 MiB. Larger disks use multiple 128 MiB block groups, with backup superblocks and descriptor tables in every group.

The stock x86 Linux 6.8.12 image exposes a VirtIO block driver, but no ATA or loop driver and no loadable module directory. Terrarium therefore implements **VirtIO block**, using the existing generic PCI transport from pinned `v86@0.5.472`. The guest uses its actual Linux block layer and filesystem driver to mount ext2. This is not a directory-shaped object store or a simulated mount.

QEMU uses its actual VirtIO block implementation with application-owned regular-file backends. A dedicated emulator worker performs synchronous bounded reads and writes through a shared-memory mailbox; the UI-side owner services them with the same `VolumeSession` used by v86. The worker receives a logical size and a fixed 64 KiB payload mailbox, without a full image copy. Reads expose committed pages, and a failed write/flush cannot produce a successful guest completion. Late read payloads and write acknowledgments from a closed generation are rejected.

There are two independently attachable data slots. Pocket PC uses reserved PCI addresses `00:0e.0` and `00:0f.0`; QEMU uses stable device serials `terrarium-volume0` and `terrarium-volume1`. Either slot can be used alone. Linux can assign `vd*` names differently in the presence of the root or evidence disk, so startup discovers the correct device through sysfs and creates stable aliases:

| Slot | Stable block-device alias | Automatic mount |
| --- | --- | --- |
| 0 | `/dev/terrarium-volume0` | `/mnt/volumes/disk0` |
| 1 | `/dev/terrarium-volume1` | `/mnt/volumes/disk1` |

Attachment and detachment require a stopped machine; block hotplug is not implemented. An unavailable or corrupt volume fails Boot explicitly. It is never replaced with an empty disk. Initialization scripts run after configured volumes mount, so they can use these paths.

Writable mounts use `rw,sync,nodev,nosuid`. Read-only mounts use `ro,nodev,nosuid,noexec`. The writable `sync` mount option reduces guest write caching but does not make a sequence of application operations atomic.

## Persistence and consistency

The volume store uses 64 KiB pages. Unallocated all-zero pages need no record. Each write commits changed pages and the volume's revision counter together in one IndexedDB transaction, requesting strict durability. The VirtIO device returns a successful write completion only after that transaction completes. Its FLUSH request waits for pending commits.

The browser and operating system still control physical storage durability and eviction. A successfully committed transaction is not a guarantee against browser data removal, origin changes, a device failure, or every possible power-loss scenario. Export important images. Volumes are local to the browser profile and site origin; publishing the same application at a different origin does not migrate them.

`syncVolumes()` first asks the running guest to execute `sync`, then briefly stops the CPU, drains outstanding VirtIO requests and IndexedDB commits, and resumes it. The operation blocks public agent commands and interactive terminal input. This flushes the current guest cache; it is not an application-level transaction or a live database backup protocol.

Workspace **Stop**, **Delete**, and **Stop & reload** sync and unmount writable filesystems before stopping the CPU and destroying the VM. A busy mount refuses the operation. Terrarium attempts to remount any disks unmounted earlier in that attempt; if repair cannot be confirmed, the machine stops with a visible error. Successful preparation holds the CPU stopped through teardown. Runtime destruction stops the CPU and drains already submitted host writes before releasing storage locks. A direct forced runtime teardown, a crashed tab, a failed command channel, or a guest that has not flushed its own cache may leave a dirty or inconsistent filesystem requiring recovery. ext2 has no journal. Images preserve their actual on-disk mount/dirty state; a snapshot does not silently repair or sanitize it.

Teardown publishes a lifecycle gate before the machine becomes idle. Boot and attachment changes remain blocked until pending requests, storage sessions and emulator disposal finish. The manager rejects duplicate lifecycle operations while destruction itself joins the same teardown rather than creating overlapping owners.

Reset retains the configured volumes. A running guest with a usable command channel is synced first; QEMU also cleanly unmounts writable data filesystems before reset. Reset of a paused guest with writable volumes is rejected until it is resumed and can sync. When the guest is already in an error state, only submitted block writes can be drained; unsubmitted guest memory cannot be recovered through the disk API. Cancelling a boot also has this forced-stop boundary. QEMU keeps a failed storage result visible and rejects the next explicit teardown attempt rather than reporting a successful deletion; a deliberate subsequent retry can finish removing the stopped definition while preserving its volume resource.

## Snapshots, clones and preservation

Volume snapshots are separate from VM memory checkpoints. Snapshot creation copies the disk bytes into a new immutable storage record and stores their SHA-256 digest. It does not overwrite the original volume. Opening a saved snapshot verifies that digest before exposing its bytes to a guest.

A writable clone is a new volume with a new storage ID and an independent copy of the source bytes. The filesystem UUID is preserved because this is a byte copy; use the stable attachment path instead of assuming a clone has a new filesystem UUID. Snapshot and clone metadata retain the source storage ID.

Copies are staged in transactions of at most 1 MiB of page payload. Destination metadata is published only with the final successful transaction. Quota failure or cancellation leaves the source and earlier snapshots intact and removes unpublished pages in bounded batches. If cleanup itself fails or the tab disappears, a durable copy journal retains the destination identity. Workspace recovery under the writer lock calls `recoverVolumeCopies()`; it skips copies whose destination Web Lock is still held, reclaims only unpublished destinations, and refuses to delete a published destination or a corrupt journal. At most four copies may be active or awaiting recovery.

The volume database keeps its original name and upgrades from schema 1 to schema 2 by adding the copy journal store. Existing metadata and pages are unchanged. A corrupt public metadata record raises an inventory error and retains its bytes; it is not silently filtered into an apparently empty inventory.

Snapshot, clone, export and deletion operations acquire an exclusive Web Lock. An attached source is rejected as busy; stop the machine before preserving or exporting its disk. Deletion also holds the workspace dependency lease, rejects configured or pending attachments, and atomically checks any supplied revision/digest conditions. Detachment removes the machine's configured reference. The source volume and snapshots remain available until explicitly deleted.

Read-only attachments use two independent protections:

1. The VirtIO device advertises `VIRTIO_BLK_F_RO`, so Linux reports a read-only block device and rejects ordinary filesystem and raw-device writes.
2. The host request handler refuses every write request for that attachment and returns a VirtIO I/O error, even if a guest bypasses its own read-only flag. It never mutates the backing bytes.

Read-only snapshot bytes are not authenticated acquisition from an external machine. The digest proves consistency with the saved preservation record, not the trustworthiness of a guest, browser profile, or user who can change the application's own storage.

Full VM checkpoint save and restore are disabled whenever any external volume is configured, including a read-only volume. The memory checkpoint format does not capture this added VirtIO device and independent disk state. Combining a memory rollback with a different disk revision would be misleading and potentially corrupting. The existing external logical-evidence attachment guard remains in place.

## Storage and resource bounds

There is no fixed count limit on saved volumes in the volume store. Browser storage quota and memory remain practical limits. The implementation accepts whole-number sizes from **4 to 8192 MiB**, with **16 MiB** as the default. Creating an empty 8 GiB disk produces 65 nonzero 64 KiB pages (4,259,840 bytes), without constructing an 8 GiB array. The two-device limit describes the reserved VirtIO attachment slots, not the number of machines or saved images.

Each open volume uses an LRU of at most **64 MiB** of committed pages. Host requests are at most **1 MiB**, pending write payloads are limited to **8 MiB**, and at most **128 operations** may be queued in a session. Queue admission fails before copying an excess payload. Cache statistics are exposed by `VolumeSession.getStorageStats()`, including peak bytes and evictions. The cache budget is not a bound on total browser process memory: guest RAM, input/output chunks, queued payloads, IndexedDB internals and browser overhead are separate allocations.

An exclusive Web Lock prevents simultaneous mutable attachments across tabs. Read-only attachments hold shared locks and can coexist. IndexedDB writes also compare the expected revision before committing; stale writers fail atomically. A quota, revision, or storage failure produces an I/O error and stops the guest with a visible error instead of acknowledging successful persistence.

The v86 request handler bounds each transfer to 1 MiB and each queue to 128 descriptors. It checks guest-memory ranges, rejects malformed requests, does not negotiate indirect descriptor tables, and cancels stale DMA completion after a driver reset. The QEMU adapter divides reads and writes into at most 64 KiB requests, allows one pending request per disk, validates sequence and ranges on the host, owns a copy of each submitted write payload, and uses a 30-second acknowledgment deadline. Its regular-file backend keeps MEMFS contents empty and records the logical size as a safe integer, including offsets above 4 GiB. A stopped owner wakes blocked workers and drains accepted host transactions before releasing attachment locks. These checks constrain the device implementations; they are not a security audit of either complete emulator.

## API

`src/lib/volume-store.ts` exports `createVolume`, `listVolumes`, `getVolume`, `snapshotVolume`, `cloneVolume`, `exportVolume`, `exportVolumeTo`, `hashVolume`, `recoverVolumeCopies`, and `deleteVolume`. The cloud control plane calls these same functions; it does not maintain a separate placeholder inventory.

```ts
const disk = await createVolume({ name: 'Agent data', sizeMiB: 16 });
await machine.runtime.attachVolume({ id: disk.id, slot: 0 });
await machine.runtime.boot();
// The guest can now read and write /mnt/volumes/disk0.
```

Use workspace/cloud Stop for an orderly guest sync before an offline snapshot. The compatibility method `exportVolume(id)` returns `{ metadata, buffer, sha256 }` for disks up to 128 MiB. Larger disks require `exportVolumeTo(id, sink, options)`, which waits for each sink write before reading the next chunk. Its result is `{ metadata, sha256, bytesWritten }`; chunks default to 1 MiB and cannot exceed it. `hashVolume` streams the same raw image without a sink. Snapshot digests retain the earlier flat SHA-256 meaning, including every implicit zero byte.

The caller owns sink completion. Close or publish the output only after `exportVolumeTo` succeeds, and abort it on failure or cancellation; snapshot integrity is checked before the function accepts the export. Do not collect a large export into a Blob or array. Browsers without a streaming file sink must show that limitation. Options include an `AbortSignal`, chunk size and progress callback. Clone/snapshot options include a signal and progress with separate `hash` and `copy` phases; copy progress measures logical address coverage, including sparse holes.

Hashing an 8 GiB logical disk still processes 8 GiB of bytes. The sparse representation bounds memory, not the cost of raw SHA-256. Opening an immutable snapshot verifies the entire digest before exposing bytes to a guest; large snapshot attachment can therefore take substantially longer than mutable attachment. This check is not skipped to meet a boot timeout.

## Provenance

The block adapter, filesystem generator and browser store are application code under Apache-2.0. Their format implementation follows the [Linux filesystem layout documentation](https://www.kernel.org/doc/html/latest/filesystems/ext4/super.html), [group descriptor format](https://www.kernel.org/doc/html/latest/filesystems/ext4/group_descr.html), and [inode layout](https://www.kernel.org/doc/html/latest/filesystems/ext4/inodes.html). No pre-existing filesystem content is incorporated.

`scripts/prepare-runtime.mjs` first verifies the exact upstream v86 library hash and then adds a deterministic constructor export, `globalThis.TerrariumVirtIO`. It does not replace upstream transport algorithms. Both the original and transformed library hashes are recorded in `public/runtime/provenance.json`, along with the source commit `cc37f35c43bf14865d74ad76879ecf9410f69eb1` and the existing BSD-2-Clause notices.

## Reproducing verification

```sh
npm ci
npm run runtime:prepare
node --experimental-strip-types --test src/lib/volume.test.ts src/lib/volume-sparse.test.ts src/lib/volume-device.test.ts src/lib/qemu-volumes.test.ts src/lib/qemu-devices.test.ts src/lib/sha256-stream.test.ts
node --experimental-strip-types scripts/smoke-volume.mjs
node --experimental-strip-types scripts/smoke-qemu-storage.mjs
```

Use Node 24.5 or newer for the smokes' real Web Locks implementation. They download the existing hash-pinned executable/guest assets into memory, or verify cached files from `TERRARIUM_VM_ASSET_DIR` for v86 and `TERRARIUM_QEMU_ASSET_DIR` for QEMU. They do not bundle those guest assets into the application.

The smoke runs actual v86 machine code, the production `LinuxRuntime`, the actual guest VirtIO/ext2 drivers and the production volume store. It verifies mount/write, Unicode and binary file data, committed pages, independent VM reopen, reset, detach, independent volume snapshots and writable clones, simultaneous writable/read-only disks, raw block-write denial, and slot 1 without slot 0. The preserved snapshot digest remains unchanged.

The QEMU smoke uses an actual emulator worker thread so the host can process IndexedDB transactions while QEMU waits on its shared-memory mailbox. It exercises persisted writes, clean shutdown/reset, independent VM reopening, slot identity, immutable snapshots, writable clones and host-protected evidence views. The current observed results are recorded in [validation](validation.md).

The Node harnesses use `fake-indexeddb@6.2.6` for IndexedDB transactions. They do not establish browser UI behavior, real browser eviction, cross-process reload persistence, or power-loss durability. Focused unit cases separately verify locking, multi-page transactions, stale-revision abort, host enforcement of read-only requests, storage-error replies, stale-DMA cancellation and QEMU acknowledgment/cancellation order. The generated 8 MiB and 128 MiB volume images, and the 32 MiB QEMU evidence view with a 1 MiB binary file, also passed host `e2fsck -fn` checks.

S2 adds `scripts/browser/s2-storage-fixture.ts`, a separate acceptance helper using the production store against actual browser IndexedDB and Web Locks. It requires a dedicated empty volume inventory. It streams 256 MiB of deterministic nonzero data across an 8 GiB logical volume, measures actual cache eviction and copy transaction payloads, and compares the complete raw export, sink and snapshot digests without collecting an 8 GiB image. Its quota/abort cases are explicitly labeled Failure injection; they do not claim physical browser quota exhaustion. Browser process memory, actual guest mounts and clean page-close/reopen persistence require their separate harness evidence. See [validation](validation.md) for commands and verification limits.
